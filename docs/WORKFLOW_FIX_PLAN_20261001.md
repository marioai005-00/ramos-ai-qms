- TechL/권태훈/thkwon, WinPAC/박영수/yspark, SSPC/기상욱/sangwook.ki, CTST/오재수/ojs 및 이메일·구분은 SUPPLIER_DIRECTORY.md를 따른다.

- 접수·첨부·심의 이력은 중앙 서버를 기준으로 한다. 브라우저 임시 저장은 작성 복구용으로만 사용한다.
- 단계 승인, PCN 승인, 보고서 결재, 외부 송부 증빙, 고객 수락은 각각 독립된 상태·이력이다.
- AI 초안 반영을 승인해도 해당 D단계가 공식 승인되는 것은 아니다. 공식 단계 결재를 별도로 진행한다.
- 사용자에게 성공을 표시하는 시점은 중앙 서버 저장/업로드/결재가 성공한 뒤이다.
- 기존 데이터·파일·감사·Git 이력을 보존한다. 근거 없는 과거 상태는 검증 필요로 표시하며 삭제하거나 실제 결재로 소급하지 않는다.
- 이메일 실제 발송은 기존 결정대로 비활성 상태를 유지한다.

## 0. 기존 기록 보존과 이전 준비

- 현재 미커밋 변경을 포함한 소스와 중앙 DB/실제 원본을 기준점으로 보존한다. 운영 중 DB 백업은 SQLite 백업 API 등 일관된 방식으로 수행한다.
- 개발·합성 데이터는 임시 DB에서만 생성하고 운영 서버와 구분한다.
- 기존 localStorage 외주 ticket은 PC/브라우저별로 수집해야 한다. 현재 PC 하나를 읽어 모든 외주사의 자료를 확보했다고 판단하지 않는다.
- IndexedDB 원본은 그 원본이 남아 있는 브라우저에서 업로드 이전을 수행해야 한다. storageKey만으로 서버 원본을 복원할 수 없다.
- 파일 이름만 있는 샘플/기록은 '원본 미등록'으로 분류한다. 파일을 임의 생성해 채우지 않는다.
- 기존 상태와 서버 승인 이벤트를 대조한다. 이벤트·버전·지정 결재자 근거가 부족한 상태는 원본 기록을 보존한 채 '재검토 필요'로 표시한다. 자동 일괄 삭제/종결은 하지 않는다.
- 이전 중복 키와 해시를 기록해 재시도해도 ticket/첨부/Case가 중복 생성되지 않게 한다.

## 1. 8D 자동 승인과 임의 완료 차단

### 수정 방식

- autonomous_8d_agent.js의 runSprint2/runSprint3/signStageInternal/submitHumanRevision 경로에서 고정 실측값·시험 PASS·타인 서명·실행완료·고객 수락 입력을 제거한다.
- reports.js의 송부 증빙 후 자동 연결은 다음 단계 검토 초안 생성/검토 안내까지만 수행하게 한다.
- 기존 Agent Runtime의 초안·검증·출처·revision 기능을 재사용한다. 과거 프런트 자동화와 중앙 Runtime에 서로 다른 공식 판정이 존재하지 않도록 연결을 통일한다.
- AI는 D4 원인 가설·추가 시험, D5 대책 후보, D6 시험 계획, D7 문서/수평전개 계획, D8 종결 확인 항목을 제안한다. 미제공 측정값은 미입력, 실행 상태는 Open/Pending으로 유지한다.
- 사람 보완요청은 대상 항목과 근거를 기록하고 보완 초안을 만든다. 기존 확인 사실과 사람 입력을 덮어쓰지 않는다.
- approval.js의 승인 판정은 현재 내용 버전/해시와 연결된 서버 승인 이벤트를 이용한다. 브라우저의 Approved/humanConfirmed만으로 완료 처리하지 않는다.
- qms_backend.py의 결재 API는 실제 중앙 Case에서 지정 결재자와 단계 순서를 조회한다. 클라이언트가 보낸 expectedApproverEmail을 결재 권한의 근거로 신뢰하지 않는다.
- 일반 저장 API에서 승인 상태/결재자/서버 이벤트를 임의 생성·변경하지 못하게 한다. 보호 필드는 서버에서 산출하고, 공식 결재 전이는 승인 API만 처리한다.
- D1~D8 선행 단계·필수 사실/원본·실제 검증 결과·권한·버전 일치를 서버에서도 검사한다. 화면 버튼 숨김만으로 통제를 끝내지 않는다.
- 승인 뒤 내용/관련 증거가 변경되면 영향을 받는 단계·보고서 버전을 재검토로 전환한다. 변경 전 서명과 출력본은 이력으로 보존한다.
- 관리자 전결은 실제 로그인 관리자, 구체적인 사유, 감사 이력을 요구한다. 미수행 시험을 PASS로 바꾸는 기능은 제공하지 않는다.

### 완료 검증

- 데모 플래그가 꺼져 있거나 켜져 있어도 운영 Case에 근거 없는 PASS/서명이 생성되지 않는다.
- 위조 승인 필드, 미지정 결재자, 누락/변조된 snapshot, 타 Case 이벤트, 이전 버전 승인으로 공식 상태를 만들 수 없다.
- 사람 승인 전후 초안 반영과 단계 승인이 서로 독립적으로 표시된다.
- 승인 내용 수정, 보완요청, 동시 변경 이후 실제 담당자 재검토를 요구한다.

## 2. 외주사 접수·공유를 중앙 API/DB로 통합

### 수정 방식

- supplier_data.js의 공식 저장 기준을 중앙 API로 바꾼다. localStorage는 폼 복구/이전 도구만 담당한다.
- 신규 테이블 예: supplier_tickets, supplier_ticket_revisions, supplier_reviews, supplier_case_links. 실제 이름/스키마는 기존 DB migration과 함께 확정한다.
- 업체/담당자/이메일은 서버의 로그인 계정과 공식 마스터에서 결정한다. 폼이 보낸 타 업체 값을 저장하지 않는다.
- ticket 번호는 서버가 고유하게 발급하고 변경마다 작성자·시각·버전·심의 이력을 보존한다.
- 제출/보완/심의는 단건 업무 API로 처리한다. 서로 다른 Case/ticket 전체를 브라우저가 덮어쓰는 방식은 사용하지 않는다.
- 최초에는 주기적 갱신으로 사내 목록/내부 알림을 업데이트하고 서버 응답 후 접수번호를 표시한다. 네트워크 오류·충돌이면 입력을 유지하고 미저장 상태를 알린다.
- 외주 담당자는 자기 업체 ticket/원본/심의 의견만 조회한다. 사내 품질 담당자는 권한 범위에 따라 조회·심의한다.
- 전체 qms/state 응답이 외주 계정에 모든 사내 Case를 제공하지 않도록 서버 응답을 제한한다. 외주 공유가 필요한 Case는 명시적으로 연결한 공개 범위만 제공한다.

### 제안 상태

임시저장 → 접수완료 → 사내검토 → 보완요청 → 보완제출 → 재검토 → 승인 또는 반려.
8D Case 연결 상태는 별도 필드로 관리하여 PCN 승인/반려 이력을 잃지 않게 한다.

### 완료 검증

- TechL/WinPAC/SSPC/CTST 각 실제 계정 제출이 별도 사내 세션에서 같은 ticket ID로 보인다.
- 업체 A가 업체 B의 ticket/원본 URL/API를 직접 요청해도 조회·수정할 수 없다.
- 재시도·더블클릭으로 중복 접수되지 않고 동시 심의로 최신 의견이 사라지지 않는다.
- 사내 접수/심의 담당 계정이 실제 서버에 등록되어 있다.

## 3. 부적합·외주사·D4 원본 파일의 공통 중앙 저장

### 수정 방식

- 공통 업로드/다운로드 API와 attachment metadata를 구현해 부적합 접수, PCN, 조립 이슈, 보완 보고서, D4 Evidence가 함께 사용한다.
- 기존 source_artifacts는 추출/출처 연결에 활용하고 실제 원본은 중앙 파일 저장소에 보관한다. DB에는 file ID, 원본명, 크기, MIME, SHA-256, 작성자, 시각, 버전과 업무 연결을 저장한다.
- 첫 구현은 한 서버의 전용 파일 디렉터리와 SQLite metadata를 사용하고 저장소 인터페이스를 분리한다. 향후 사내 NAS/다른 저장소로 교체 가능하게 한다.
- 서버 런타임 DB와 원본은 지정한 서버 저장소에서 운영한다. 소스/문서는 기존 Mario 프로젝트 폴더로 관리하고 인증값은 PC별 비밀 저장소로 관리한다.
- 파일 경로는 공개 정적 웹 경로와 분리하고, 로그인·업체/Case 권한을 검사하는 다운로드 API를 통해 제공한다. 사용자 파일명을 실제 저장 경로로 사용하지 않는다.
- 파일 선택/업로드 상태를 표시하고 완료된 file ID만 ticket/Case에 연결한다. 파일 0건이면 0건으로 저장한다.
- 누락된 handleSupplierFileUpload를 공통 업로드 기능에 연결하고 고정/샘플 첨부명 및 허위 완료 메시지를 제거한다.
- 크기·형식 제한은 화면과 서버에 동일하게 적용한다. 큰 파일은 요청 한도에 맞는 업로드 경로로 처리하고 현재 JSON 본문 한도에 무조건 base64로 넣지 않는다.
- 부분 실패하면 입력/업로드 성공분을 보존하고 최종 제출완료는 표시하지 않는다. 임시 미연결 원본 정리 정책과 중복 처리 규칙을 둔다.
- 보완 제출은 이전 원본을 덮어쓰지 않고 새 버전으로 연결한다. 심의 의견과 제출 버전이 대응하도록 보존한다.

### 완료 검증

- 외주 PC에서 올린 PDF/Excel/이미지/CSV가 사내 다른 PC에서 열리고 다운로드 SHA-256이 일치한다.
- 사내 부적합 원본과 D4 Evidence도 다른 권한자 PC에서 같은 file ID로 조회된다.
- 업로드 실패/새로고침/브라우저 종료/재시도 시 원본이 다른 ticket에 연결되거나 거짓 제출완료가 생기지 않는다.
- 승인 후 Evidence 교체는 이력/재검토를 남기고 과거 보고서는 당시 원본 버전을 참조한다.

## 4. PCN 심의와 조립 이슈의 8D 연결

### 수정 방식

- PCN은 변경 대상, 변경 전/후, 사유, 적용 예정일, 영향 제품/고객/LOT와 관련 시험 자료를 심의한다. PCN 접수가 자동으로 8D 필요 판정이나 고객 승인 완료가 되지 않게 한다.
- 조립 이슈는 공정/현상/LOT/확인 수량/실행된 초동조치/원본을 받으며 품질 담당자가 심각도와 8D 필요 여부를 판정한다.
- 품질 담당자는 '기존 Case 연결' 또는 '새 Case 생성'을 선택한다. 고정 데모 ID와 CURRENT_CASE에 의존하는 경로를 제거한다.
- 서버가 Case ID를 생성하고 ticket 링크/Case 사실/Evidence 연결을 하나의 업무 처리로 저장한다. 중복 클릭은 같은 연결 결과를 반환한다.
- 원본 ticket은 보존하고 Case D2/D3에는 확인된 사실과 출처 링크를 반영한다. 미확인 원인/계측/봉쇄 결과는 가설 또는 미확인으로 남긴다.
- PCN과 D5 변경관리의 연결은 승인 ticket/정식 변경 증빙을 사용한다. PCN 승인이 8D D5 결재나 고객 수락을 대신하지 않는다.

### 완료 검증

- 선택/생성한 Case ID가 ticket과 일치하고, 해당 Case에만 D2/D3 사실·원본이 연결된다.
- 다른 Case와 기존 승인 내용을 덮어쓰지 않는다.
- 연결·원본 변경·보완 이력이 조회되고 8D 단계는 실제 결재 전 검토 상태다.

## 5. 원본 기반 AI·보고서·실제 접속

### AI와 보고서

- supplier_ai_audit.js의 benchmark/파일명 점수를 제거하고 실제 본문·표·이미지와 출처를 바탕으로 검토 초안을 생성한다.
- 실제 자료의 외부 AI 전송은 기존 정책대로 사용자 확인 후 수행한다. 실패 시 입력/원본을 유지하고 사람 검토로 이어진다.
- AI가 제시한 원인·적합성·대책은 가설/추천으로 표시하고 어떤 원본/페이지/표에서 근거를 얻었는지 보여준다.
- 보고서 데이터와 첨부는 현재 Case 및 확정 버전에서 읽는다. 미결재 출력은 DRAFT, 공식 발행은 해당 버전의 실제 결재를 통과한 경우에만 허용한다.
- Initial 3D → Interim 5D → Final 8D는 각각 당시 미확인·미완료 항목을 포함하며 출처·결재 이력을 추적할 수 있어야 한다.
- 고객 송부 증빙/송부 준비 상태와 고객 수락 상태를 구분한다. 실제 이메일 연결은 이후 공급자 결정에 따라 별도 구현한다.

### 접속과 운영

- 현재 localhost launcher는 다른 회사 PC가 접속하는 운영 구성이 아니다. 하나의 상시 중앙 서버와 승인된 접속 URL을 준비한다.
- 권장 목표는 외주 담당자가 각 회사 PC에서 로그인하는 방식이다. 회사의 허용된 원격 접속 방식, HTTPS URL, 서버 호스트/저장소 위치는 운영 환경에 맞춰 확정해야 한다.
- 단순 포트 개방으로 전환하지 않고 Host/Origin 허용 목록, 세션·CSRF, 업체별 조회/변경 권한을 배포 설정과 함께 적용한다.
- 계정별 비밀번호/초기 변경 절차, 사내 접수·심의/Case 지정 결재자 계정, DB+원본 백업/복원을 준비한다.
- 사내 담당자와 외주사 각각의 실제 네트워크에서 로그인·조회·업로드·다운로드를 확인해야 운영 접속 완료로 판정한다.

## 최종 업무 흐름과 인수 기준

외주 담당자 실제 로그인 → PCN/조립 이슈 + 실제 원본 제출 → 사내 품질 담당자 조회/원본 검토 → 보완요청 → 외주 보완 제출 → 심의 → 필요한 건의 Case 선택/생성 → D1~D8 초안/사람 입력/실제 단계 결재 → 해당 버전 보고서 결재·출력 → 외부 송부 증빙/필요한 고객 수락.

| 검증 시나리오 | 통과 조건 |
| --- | --- |
| 4개 업체 각각 접수 | 업체/담당자/분류/이메일 일치, 서버 고유번호, 사내 별도 세션 조회 |
| 업체 간 분리 | 다른 업체 ticket/원본/내부 Case의 직접 API 조회·변경 차단 |
| 실제 파일/보완 | 원본 해시 일치, 파일 0건 허위 생성 없음, 이전 버전 유지 |
| 잘못된/부분 실패 요청 | 입력 유지, 중복 없음, 성공 오표시 없음, 임시 파일 복구/정리 |
| Case 연계 | 지정 Case만 업데이트, 최초 원본과 ticket 출처 유지 |
| AI 안전성 | 입력하지 않은 시험 PASS/완료/승인/고객 수락 생성 없음 |
| 실제 결재 | 권한·지정자·순서·내용 버전을 서버에서 확인, 다른 사용자 명의 서명 불가 |
| 수정/동시 작업 | 최신 데이터 덮어쓰기 차단, 기존 승인 재검토 및 이력 유지 |
| 보고서 | 초안 DRAFT, 공식판은 실제 승인 버전·원본과 일치 |
| 운영 접속/복원 | 외주/사내 실제 PC 접속, 계정별 권한, DB+원본 복원 후 업무 조회 |

기존 35개 Python 회귀 테스트에 위 조건을 추가한다. 브라우저 E2E는 단일 세션의 계정 변수 교체나 강제 승인 fixture를 쓰지 않고 별도 실제 서버 로그인과 서로 분리된 브라우저 세션으로 실행한다.

## 재사용 대상과 수정 파일 범위

- 재사용: portal_server.py의 서버/인증, qms_backend.py의 DB/감사/버전/실제 결재 이벤트, agent_runtime.py의 초안/출처/품질 finding/revision.
- 강화: qms_backend.py/portal_server.py의 단건 접수·원본·업체별 권한·결재 서버 검증·DB migration.
- 연결: js/server_api.js, js/supplier_data.js, js/intake_documents.js, js/views/d4_evidence.js, js/views/supplier_portal.js, js/views/supplier_ai_audit.js.
- 자동화 수정: js/views/autonomous_8d_agent.js, js/approval.js, js/views/reports.js 및 단계/연계 화면.
- 검증/문서: 신규 API/권한/첨부/승인 회귀 테스트와 실제 다중 사용자 E2E, 인수인계/운영 설정 문서.

기존 기능을 유지하는 작은 수정 단위로 진행하며 각 단위에 실패 재현 테스트와 완료 증빙을 남긴다. 작업 시간이나 완료 날짜는 운영 서버/자료 이전 범위가 확정된 후 산정한다.

## 아직 결정할 운영 항목

- 중앙 서버를 실행할 호스트와 상시 운영 담당, 런타임 DB/원본 저장 경로.
- 외주사 각 회사 PC에서 허용되는 접속 방식과 실제 URL.
- PCN 최종 심의자/결재 순서 및 내부 Case의 외주 공유 범위.
- 업로드 허용 형식/크기와 실제 파일 처리·보관 정책.
- 외부 AI에 전달 가능한 자료 범위와 운영 전 검증 자료.

이 항목들은 구현 방향의 가정을 명시한 것으로, 사용자/회사 확정 전 배포나 외부 자료 송신을 실행하지 않는다. 우선순위 1~4의 코드·임시 환경 검증 계획은 독립적으로 구체화할 수 있다.
